## 2. ไฟล์ที่สร้างในรอบนี้

### `backend/common/permissions.py` — Role-based DRF permissions
- **Base:** `IsRole(BasePermission)` — เช็ค 3 เงื่อนไข: มี `request.user`, `is_authenticated`, `is_active` แล้วเช็ค role
  - `allowed_roles` (frozenset) + `admin_can_impersonate` = class attributes (declarative — subclass แต่ละตัวแค่ประกาศ)
  - **fail-safe:** base default = `allowed_roles=∅` + `admin_can_impersonate=False` → ลืม config = ทุกคนถูกปฏิเสธ
- **Subclasses:** `IsHomestayOwner`, `IsRestaurantOwner`, `IsWellnessOwner`, `IsOtopOwner` (`admin_can_impersonate=True`), `IsTourist`, `IsCommunityAdmin`, `IsSuperAdmin` (`False`)
- **ทำไมเป็น subclass ไม่ใช่ factory `IsRole(*roles)` ตามที่ C3 เขียน:** DRF `permission_classes` ต้องเป็น *class* (DRF instantiate เองทุก request) → instance ของ factory ใช้ไม่ได้; subclass + base class ได้ทั้ง DRY และอ่านง่ายกว่า
- **การตัดสินใจนโยบาย (user เลือก):**
  - SUPER_ADMIN ทะลุผ่าน **4 role ผู้ขาย** ได้ (ช่วย vendor จัดการ content) แต่ **ไม่ผ่าน `IsTourist`** (flow เงินต้องเป็นของ tourist จริง)
  - COMMUNITY_ADMIN ไม่ทะลุ role ผู้ขาย (ไม่มีสิทธิ์นั้น)
  - `IsCommunityAdmin`/`IsSuperAdmin` เตรียมไว้เผื่อ portal ฝั่ง admin (ยังไม่มี endpoint ใช้ — กัน scope creep)

### `backend/common/pagination.py` — `StandardPagination(PageNumberPagination)`
- **ทำไมต้อง custom:** DRF default คืน `{count, next, previous, results}` ไม่ตรง envelope spec §4 → ห่อผ่าน `api_success(..., meta={"pagination": {...}})`
- **ทำไม PageNumber (ไม่ใช่ LimitOffset):** spec ใช้ `page` + `total_pages` ตรงกับ Django Paginator; LimitOffset ไม่มี field `page` ต้องคำนวณย้อนกลับ
- Config: `page_size=20`, `page_size_query_param="limit"` (`?page=1&limit=50`), `max_page_size=100` (กันดึงทั้งตาราง)
- `total_pages = max(1, num_pages)` — list ว่าง Django คืน 0 แต่ `page.number=1` → floor ไว้ 1 กัน FE สับสน
- **วิธีใช้:** CBV → `pagination_class = StandardPagination`; FBV → `StandardPagination().paginate_queryset(qs, request, view)` แล้วคืน `get_paginated_response(data)`

## 3. การตัดสินใจ + WHY (สรุปย่อ)

1. Permission logic อยู่ที่ **base class** จุดเดียว (DRY) — subclass แค่ประกาศค่า กัน logic ซ้ำ/เพี้ยน
2. เช็ค `is_active` ใน permission ด้วย — กันบัญชี soft-delete ยังใช้ token เดิมยิง API ต่อได้ (ZERO TRUST)
3. `IsTourist` ปิด admin bypass — booking/จ่ายเงิน audit ต้องเป็นของผู้ใช้จริง
4. fail-safe default — ความผิดพลาดต้อง "ปิด" ไม่ใช่ "เปิด"

## 5. Slice 2 (accommodations) — ไฟล์ที่สร้าง/แก้ในรอบนี้

### `backend/common/views.py` (ใหม่) — `EnvelopeMixin`
- CBV (generics/APIView) คืน data เปล่า → mixin นี้ wrap **2xx** เป็น envelope `{success,data,message}` ให้ CBV ทุกตัว (error 4xx/5xx มี `common/exceptions.py` อยู่แล้ว)
- เช็คว่า data มี key `success` แล้ว (เช่นจาก `StandardPagination`) → ข้าม ไม่ wrap ซ้ำ

### `backend/apps/accommodations/serializers.py` (ใหม่)
- `RoomImageSerializer` (read-only — รูปยังเป็น URL string ไม่มี upload ใน Phase 1)
- `AccommodationSerializer` — `owner/slug/status/created_at` read-only; `min_price_per_night`/`room_count` จาก prefetch `active_rooms`
- `RoomSerializer` — **บังคับส่ง `base_capacity`+`max_capacity`** (กันส่งตัวเดียวแล้ว model default=2 มาทำให้ `max<base` โดยไม่มี error); `accommodation` FK inject โดย view
- `RoomPublicSerializer` — เพิ่ม `availability` (per-night) + `total_price_for_stay` (อ่านจาก attr ที่ view stash บน instance)
- `RoomPricingSerializer` — `{date, price_override?, available_count?}`

### `backend/apps/accommodations/views.py` (ใหม่)
- Pattern = **แบบผสม** (user เลือก): list/create CRUD = CBV; pricing = FBV
- `AccommodationListCreateView(EnvelopeMixin, generics.ListCreateAPIView)`:
  - GET public: filter `status=ACTIVE` + `province` + `guests` (rooms max_capacity) + `min/max_price` (room ถูกสุด active ผ่าน Subquery) + `checkin/checkout` (ต้องมีห้องว่างครบทุกคืน) → `StandardPagination` + prefetch
  - POST: `IsHomestayOwner` + `owner=request.user`
- `AccommodationRoomsView(EnvelopeMixin, APIView)`: GET = ต้อง ACTIVE + คืน rooms พร้อม availability/ราคา (query calendar bulk ครั้งเดียวกัน N+1); POST = เจ้าของเท่านั้น
- `room_pricing_view` (FBV): `transaction.atomic()` + **ล็อก Room row ก่อน** (lock ordering ตรงกับ checkout กัน deadlock); update เฉพาะ field ที่ส่ง (ไม่รีเซ็ตของเหลือ); `price_override=null` = ล้างกลับราคาฐาน; `available_count` validate `0..total_inventory`

### `backend/apps/accommodations/urls.py` + `backend/core/urls.py`
- mount `/api/v1/accommodations/` → `""`, `<uuid>/rooms/`, `rooms/<uuid>/pricing/`

## 6. Slice 2 — การตัดสินใจ/WHY + จุดที่ต้องรู้ต่อ

1. **`_can_manage_accommodation()`** — SUPER_ADMIN ผ่านเสมอ (สอดคล้องกับ permission ที่เปิด role gate ให้ admin — ไม่งั้นผ่าน gate แต่โดน owner check); COMMUNITY_ADMIN/คนอื่นต้องเป็นเจ้าของ

## 11. Step 4 (Celery + 15-min expiry worker) — สรุป

### ไฟล์
- `core/celery.py` (ใหม่) + `core/__init__.py` (แก้ — import celery_app) + `core/settings/base.py` (แก้ — CELERY_BROKER_URL/TIMEZONE/ALWAYS_EAGER)
- `requirements/base.txt` (แก้ — celery + redis)
- `apps/bookings/tasks.py` (ใหม่) — `expire_booking_task`
- `apps/bookings/services.py` (แก้) — `release_inventory_for_booking()` + scheduling ตอน checkout
- `apps/payments/services.py` (แก้) — `verify_slip` lock Booking ก่อน Payment

### การตัดสินใจ/WHY
1. **fail-fast:** schedule งาน **ภายใน atomic ก่อน commit** — broker ล่ม = rollback booking ทั้งหมด (booking ค้างไร้ task = inventory รั่ว) — ต่างจาก C3 ที่เขียน `on_commit` (ขออนุมัติจาก user แล้ว)
2. **idempotent task:** เช็ค booking เจอ/status/expires_at ก่อน → รันซ้ำ/รันเร็ว/race กับ verify_slip ไม่พัง ไม่ double-restore
3. **lock ordering:** expiry = lock Booking ก่อน → inventory; `verify_slip` ปรับตาม (lock Booking → Payment → slip) → กัน deadlock (C2 §2.3)
4. **`.env`:** `CELERY_TASK_ALWAYS_EAGER=True` (user เลือก — ไม่ต้องติดตั้ง Redis ตอนนี้; booking ไม่ expire อัตโนมัติใน dev แต่ production ต้องรัน Redis+worker จริง)
