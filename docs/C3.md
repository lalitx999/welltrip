## 3. ข้อตกลงเชิงเทคนิคที่ทำไว้แล้ว (อย่าเปลี่ยนโดยไม่ถาม)

1. **Payment = Slip Check ล้วน** (เลิก Omise/EMVCo)
   - `Payment.channel=BANK_TRANSFER`; `PaymentSlip` เก็บรูป+provider log+`provider_reference`
   - `_call_slip_provider()` ยังไม่ implement (รอ vendor) — `verify_slip(provider=...)` inject ได้
   - Normalized payload contract: `{amount, trans_ref, trans_datetime?, sender_name?}`
2. **`BookingItem.entity_id` = `CharField(36)`** เก็บ canonical string เนื่องจาก PK ต่างชนิด:
   - `ROOM_RESERVATION`/`FOOD_ORDER`/`OTOP_GOODS` → target PK เป็น UUID → cast `uuid.UUID(entity_id)`
   - `WELLNESS_SESSION` → target PK เป็น int (BIGSERIAL) → cast `int(entity_id)`
3. **Inventory semantics** (ทุก domain ใช้หลักเดียวกัน):
   - แถว calendar/slot/capacity = "ของเหลือจริง" → row ไม่มี = ว่างเต็ม (`total_inventory` / `max_capacity_per_session`)
   - checkout decrement ทันทีที่สร้าง Booking; expiry worker restore (Step 4)
4. **Domain helpers ที่เขียนแล้ว** (Step 3 ต้องเรียกใช้ ไม่เขียน logic ซ้ำ):
   - `apps/accommodations/services.py`: `calculate_room_availability(room_id, ci, co, lock=False)`, `get_total_room_price(...)`
   - `apps/services/services.py`: `get_wellness_slots(service_id, slot_date)`, `create_wellness_time_slot(...)`
   - `apps/otop/services.py`: `reserve_stock`, `restore_stock` (ต้องอยู่ใน transaction)
   - `apps/bookings/services.py`: `execute_atomic_checkout(cart_items, user)`, `CheckoutError(code,message,details)`
   - `apps/payments/services.py`: `create_bank_transfer_payment`, `create_slip`, `verify_slip`
5. **สถานะ transitions ปัจจุบัน:** slip VERIFIED → `Payment=SUCCESS` + `Booking=CONFIRMED` (อยู่ใน `payments/services.verify_slip`)
6. **Booking ยังไม่ schedule Celery** (จะเพิ่มใน Step 4)
7. `platform_fee=0` ยังไม่มี policy
8. conventions: UUID PK สำหรับ entity; BigAuto สำหรับ child rows (image/calendar/slot/booking_item); `db_table` ตาม spec; related_name ชัดเจน; `settings.AUTH_USER_MODEL` เสมอ; ใช้ `Decimal` สำหรับเงิน; validate type/range ก่อนแตะ DB

### 5.4 การ map error จาก services → HTTP (ต้องทำใน views)

- Serializer `ValidationError` → DRF จัดการเอง → envelope อัตโนมัติ (ผ่าน `common.exceptions.standardized_exception_handler`)
- `CheckoutError` (จาก bookings) → map:
  - code ใน `{EMPTY_CART, INVALID_ITEM, INVALID_ITEM_TYPE}` → **400**
  - `{ROOM_UNAVAILABLE, SLOT_UNAVAILABLE, STOCK_UNAVAILABLE, ITEM_UNAVAILABLE}` → **409** (spec: abort 409 conflict)
  - default → 400/422
- `ValueError`/`TypeError` จาก service (เช่น date ผิด, capacity เกิน) → **400** envelope
- `*.DoesNotExist` → **404** (จับใน view หรือปล่อยให้ DRF Http404)
- `NotImplementedError` จาก `_call_slip_provider` → **503** (provider ยังไม่ configure) + message ชัดเจน "ยังไม่ได้ตั้งค่า Slip Check provider"
- แนะนำ: เขียน helper สั้น ๆ ใน `common/responses.py` หรือ view module สำหรับ map นี้ (ถาม user ถ้าจะวางตรงอื่น)

[

## 6. STEP 4 PLAN: Celery + 15-min Expiry Worker

### 6.1 สิ่งที่ต้องเพิ่ม (R0 user รัน/ติดตั้ง)
- requirements: `celery>=5.4,<6` + `redis>=5,<6` → `pip install` (user รัน) แล้ว append ใน `requirements/base.txt`
- ไฟล์ใหม่:
  - `backend/core/celery.py` (standard Celery app: `broker=settings.CELERY_BROKER_URL`, timezone เดียวกับ Django)
  - `backend/core/__init__.py`: `default_app_config`/import celery (ระวัง circular import — ใช้ pattern `from .celery import app as celery_app`)
  - `backend/apps/bookings/tasks.py`
- settings/base.py: `CELERY_BROKER_URL = env("CELERY_BROKER_URL", default="redis://127.0.0.1:6379/0")`, `CELERY_TIMEZONE = TIME_ZONE`, result backend ไม่จำเป็น phase นี้
- dev อาจใช้ `CELERY_TASK_ALWAYS_EAGER` ผ่าน .env/local ถ้าต้องการ (แต่ระวัง: eager = รันทันที ไม่เหมาะกับ countdown) → แนะนำ dev รัน redis + worker จริง

### 6.2 งาน worker: `expire_booking_task(booking_id)`
- `@shared_task`
- Logic (ใน `transaction.atomic()`):
  1. `select_for_update()` หา `Booking` ที่ `status=AWAITING_PAYMENT` + `expires_at <= now` → ถ้าไม่มี/no-op คืน
  2. เปลี่ยน `Booking.status = PAYMENT_EXPIRED`
  3. คืน inventory ทุกรายการ → เรียกฟังก์ชัน release (แนะนำวางใน `apps/bookings/services.py`: `release_inventory_for_booking(booking)` เพื่อให้ test ได้โดยไม่ต้องผ่าน task)
     - ไล่ `booking.items` + **cast entity_id ตาม item_type** (หัวข้อ 3.2 ของไฟล์นี้):
       - `ROOM_RESERVATION`: restore `RoomPricingCalendar.available_count += quantity` สำหรับทุกคืนใน `[scheduled_date, scheduled_end_date)` (แถวต้องมีอยู่เพราะ checkout สร้างไว้)
       - `WELLNESS_SESSION`: `WellnessTimeSlot.capacity_available += quantity`
       - `OTOP_GOODS`: เรียก `otop.services.restore_stock(...)`
       - `FOOD_ORDER`: ไม่มี inventory
  4. ถ้า Payment ของ booking ยัง `PENDING` → ตั้ง `Payment.status = EXPIRED`
  5. (FCM แจ้งเตือนยังไม่ทำ — ไม่มี infra notifications; จด TODO)
- Lock ordering (สำคัญ): ตกลงให้ **lock Booking row ก่อน** เสมอ → Step 4 ต้องปรับ `payments/services.verify_slip` ให้ lock booking row ในลำดับเดียวกัน (ตอนนี้ lock payment ก่อน) เพื่อกัน deadlock — **ถาม user ก่อนปรับ** เพราะแตะโค้ดที่เทสต์ผ่านแล้ว

### 6.3 schedule จาก checkout
- เพิ่มใน `execute_atomic_checkout` **หลัง** transaction commit:
  `transaction.on_commit(lambda: expire_booking_task.apply_async(args=[str(booking.id)], countdown=BOOKING_TTL_MINUTES * 60))`
- import tasks แบบปลอดภัย (lazy หรือ module ที่ไม่วนซ้ำกับ services)
- ถ้า broker ไม่พร้อม: ควร log error ไม่ทำให้ response 500 (ถาม user ว่าให้ fail-fast หรือ log แล้วเก็บไว้)

### 6.4 เทสต์ (user รัน)
- รัน redis + worker: `redis-server` และ `celery -A core worker -l info` (user)
- เทสต์: สร้าง booking → แก้ `expires_at` ให้เป็นอดีต → รัน task → booking=PAYMENT_EXPIRED + inventory คืน + payment=EXPIRED
- ทดสอบ race: อัปสลิป กับ task ทำงานพร้อมกัน → ผลต้อง consistent (ล็อกเดียวกัน ไม่ deadlock)

- Zod schemas: date range, cart, slip upload form (ตาม spec §8.1) ใน `frontend/src/schemas/`

### 7.3 หมายเหตุ
- Cart เป็น multi-vendor → UI ต้องจัดกลุ่มตาม vendor (ถ้าต้องการ) — backend ตอนนี้ items เก็บ vendor ไว้แล้ว แต่ checkout API ไม่ต้องการ vendor grouping
- ค่าคงที่ status/enum ให้ copy จาก backend เป็น union type ใน `types/` เดียว (กัน drift) หรือ comment ให้ sync กัน

## 8. STEP 6 PLAN: Tourist Routes (Mobile-First)

> วางใต้ route group ที่มี bottom nav (จาก spec: `(mobile-tourist)`) — ดูโครงสร้าง FE จริงก่อน เพราะตอนนี้มีแค่ `/home` placeholder + `(auth)`
> **เปลี่ยนจาก spec เดิม:** flow จ่ายเงินเป็น Slip Check → **ไม่มีหน้า QR** อีกแล้ว ต้องเปลี่ยนเป็นหน้า "รายละเอียดบัญชีผู้รับ + อัปสลิป" — ขอชื่อ route/UX กับ user ก่อน (แนะนำ `(mobile-tourist)/checkout/payment/[bookingId]`)

| Route | ฟีเจอร์ | หมายเหตุ/Icon |
|---|---|---|
| `/home` | search bar + category cards (Hotels/Foods/Wellness/OTOP) | `<Compass/>`, `<Search/>` |

| `/foods`, `/foods/[id]` | list กรอง category/max_calorie, detail + add-to-cart | `<UtensilsCrossed/>`, `<Salad/>`, `<Flame/>`, `<Apple/>` |
| `/wellness`, `/wellness/[id]` | list + detail เลือกสล็อต (วัน+เวลา) ดู capacity → cart | `<Sparkles/>`, `<Clock/>`, `<HeartPulse/>`, `<Bath/>` |
| `/otop`, `/otop/[id]` | list search/category + detail + qty → cart | `<ShoppingBag/>`, `<Package/>`, `<Tag/>`, `<Store/>` |
| `/cart` | multi-vendor cart, จัดกลุ่ม vendor, แก้จำนวน/ลบ, สรุปยอด | zustand persist; สรุปย่อยแยก vendor |
| `/checkout` | สรุปรวม + เลือกช่องทาง (เฉพาะ bank transfer) → POST checkout → ไปหน้า payment | เรียก `POST /bookings/checkout/` |
| `/checkout/payment/[bookingId]` (ใหม่) | แสดง booking_code + เลขบัญชี/ชื่อ/ธนาคารผู้รับ + 15-min countdown (ใช้ `expires_at`) + อัปสลิป (multipart) + ตรวจผล VERIFIED/REJECTED + ปุ่ม "ไป my-bookings" | `<CreditCard/>`, `<ShieldCheck/>`, `<Upload/>` (หรือไอคอนที่เหมาะสม) |

### หมายเหตุ integration
- ใช้ TanStack Query เป็น server cache; axios instance เดิม (มี silent refresh)
- Zod schema ตรวจวันที่/ฟอร์ม (spec §8.1) — `checkout_date > checkin_date`, จำนวน > 0
- Enum/status ต้อง sync กับ backend (union type ใน `types/`)
- Touch target ≥ 44px, `max-w-md mx-auto`, safe-area bottom nav
- **ห้าม Emoji** — ใช้ Lucide เท่านั้น (ตารางไอคอนมีใน `Phase1.md` §7.2)

## 9. STEP 7 PLAN: Vendor Portal (`/portal`)

> ต้องมี API ก่อน (Step 3–4) + **ถาม user** เรื่อง "vendor endpoint ดู incoming orders" (blocker หัวข้อ 4)

| Route | ฟีเจอร์ | ข้อมูลจาก API |
|---|---|---|
| `/portal/homestay` | dashboard incoming bookings + Approve/Reject?, room calendar + ตั้งราคา/ปิดห้อง (pricing endpoint) | POST pricing; (incoming orders — รอตกลง endpoint) |
| `/portal/restaurant` | รายการเมนู + toggle Available/Sold-out (`is_available`), ดู orders | PATCH foods /my-menus? (ต้องออกแบบ endpoint ย่อยเอง — ถาม user) |
| `/portal/wellness` | service list + สร้างสล็อต (manual form: date+start+end+capacity), ดู capacity | POST `/wellness/{id}/slots/` |
| `/portal/otop` | inventory CRUD + ปรับ stock, SKU tracking | POST `/otop/` + endpoints PATCH/stock (ต้องออกแบบเพิ่ม — ถาม user) |

### หมายเหตุ
- Sidebar ตาม role (คนเดียวมีได้หลาย role? ปัจจุบัน User.role เป็นค่าเดียว → portal เข้าตาม role ที่ login)
- สถานะ "incoming bookings" ของ vendor: spec ยังไม่มี endpoint ชัดเจน → **ออกแบบร่วมกับ user** (เช่น `GET /api/v1/vendor/orders/?role=HOMESTAY_OWNER`) — ห้ามเดาเอง
