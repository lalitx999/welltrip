# WellTrip — Phase 1: Authentication & User Management (Summary)

> **ประเภทเอกสาร:** สรุปงานส่งต่อ (handover) — ใช้ได้ 2 กรณี:
> 1. ให้ AI ตัวอื่นอ่านต่อโดยไม่ต้องอธิบายซ้ำ
> 2. ให้เพื่อนร่วมทีม / เจ้าของโปรเจกต์อ่านย้อนหลัง
>
> **ตำแหน่งโค้ด:** `backend/` (Django) + `frontend/` (Next.js) ใน repo `welltrip`
> **สเปกอ้างอิง:** `Phase1.md` (Master System Architecture — Clean Version)

---

## 1. ภาพรวมของ Phase 1

### วัตถุประสงค์
สร้างระบบ **Authentication & User Management** แบบ mobile-first สำหรับแพลตฟอร์มท่องเที่ยวเชิงสุขภาพ WellTrip รองรับการเข้าสู่ระบบ 2 ช่องทาง:
1. **Email/Password** (สมัครด้วยตนเอง)
2. **Google OAuth** (ตรวจสอบ `id_token` ฝั่ง server ด้วย `google-auth`)

### งานที่ทำเสร็จแล้ว (สรุปสั้น)
- **Backend (Django):** โปรเจกต์ Django + Custom User Model (UUID PK, role enum, `google_sub_id`, password=NULL ได้) + 4 API (register / login / refresh / oauth.google) + error envelope มาตรฐาน spec §8.2 + แยก settings base/local/production + secret อ่านจาก `.env` (SECURITY FIRST)
- **Frontend (Next.js):** Landing, Login, Register, Google Callback, post-login placeholder `/home` + Axios silent refresh (single-flight) + Zustand auth store + Zod/RHF + **ปุ่มภาษา TH/EN** (default ไทย) + theme แบรนด์ (#FF7444 / #FFF8DE / ฟอนต์ Kanit)
- **อัปเกรดระหว่างทาง:** Next.js **16.3.4 (Turbopack)** + React **19** + ธีมสีแบรนด์ + i18n
- **การทดสอบ:** Backend test **10/10 ผ่าน**; Frontend `typecheck` + `build` ผ่าน

> หมายเหตุขอบเขต: email verification, FCM, role permission, rate limiting **ยังไม่ทำ** (ดูหัวข้อ 10)

## 4. API Endpoints ที่สร้างเสร็จแล้ว

> หมายเหตุ: ทุก response อยู่ใน **envelope มาตรฐาน** ของโปรเจกต์ (spec §4)  
> Success: `{ "success": true, "data": {...}, "message": "..." }`  
> Error: `{ "success": false, "error": { "code": "...", "details": {...} }, "message": "..." }`

| Method | Path | Auth | Request Body | Response `data` | คำอธิบาย |
|---|---|---|---|---|---|
| POST | `/api/v1/auth/register/` | Public | `{ email, password, first_name?, last_name?, phone_number? }` | `{ user }` (HTTP 201) | สมัคร Email/Password — **ไม่คืน token** (ต่างจาก template: ต้องไป login ต่อ) |
| POST | `/api/v1/auth/login/` | Public | `{ email, password }` | `{ user, access_token, refresh_token }` | เข้าสู่ระบบ รับ JWT |
| POST | `/api/v1/auth/oauth/google/` | Public | `{ id_token }` | `{ user, is_new_user, access_token, refresh_token }` | ตรวจ Google ID token แล้ว login / สร้าง user อัตโนมัติ |
| POST | `/api/v1/auth/refresh/` | Public | `{ refresh }` | `{ access_token, refresh_token }` | ต่ออายุ + **rotation** (refresh token เก่าถูก blacklist ทันที) |
| ~~POST~~ `/logout/` | — | — | — | — | **ยังไม่ได้สร้าง** (TODO ดูหัวข้อ 10) |
| ~~GET~~ `/me/` | — | — | — | — | **ยังไม่ได้สร้าง** (TODO ดูหัวข้อ 10) |

**URL mount:** `core/urls.py` → `path("api/v1/auth/", include("apps.authentication.urls"))`  
**Auth scheme:** `Authorization: Bearer <access_token>` (ผ่าน SimpleJWT) — ยังไม่มี endpoint ที่ต้อง auth ในเฟสนี้

## 5. Business Logic & กฎสำคัญที่ใช้

1. **การสมัคร (register):** email ถูก normalize เป็น lowercase → ตรวจ unique → password ผ่าน `validate_password()` (Django validators) → สร้าง user **role=TOURIST**, `is_verified=False`; `username` **auto-generate จาก email** (`services.build_unique_username`) — client ไม่ต้องส่ง
2. **Password hashing:** ใช้ **PBKDF2 (default Django)** — ยังไม่ปรับ Argon2
3. **Login:** email+pw → `authenticate()` ของ Django (เช็ค hash + `is_active`); user ที่เป็น **Google-only (password=NULL)** โดนปฏิเสธด้วย code `GOOGLE_ONLY_ACCOUNT`
4. **Google OAuth** (`services.authenticate_with_google`):
   - ตรวจ `id_token` กับ Google certs โดยใช้ `GOOGLE_OAUTH_CLIENT_IDS` เป็น audience + ต้อง `email_verified=True`
   - หา user ด้วย `google_sub_id`: เจอ → login
   - ยังไม่มี → หาด้วย email: เจอบัญชี manual เดิม → **link `google_sub_id` + ตั้ง `is_verified=True`** (ไม่แตะ password เดิม)
   - ไม่เจอเลย → **สร้าง user ใหม่: password=NULL**, เอา name จาก Google claims
   - ⚠️ โค้ดจริง **ไม่** อัปเดต first_name/last_name/picture ของ user เก่า และ **ไม่มี field picture** (ต่างจาก template — ดู TODO)
5. **JWT:** Access **15 นาที**, Refresh **7 วัน** (ตั้งค่าได้ใน `.env`); `ROTATE_REFRESH_TOKENS=True` + `BLACKLIST_AFTER_ROTATION=True` → token เก่าตายทันที
6. **Silent refresh (frontend):** Axios response interceptor เจอ 401 → refresh ครั้งเดียว (single-flight กัน refresh storm) → replay request
7. **Soft-delete:** ยังไม่มี — เตรียม `is_active` ไว้ (spec กำหนดห้าม hard delete เมื่อมี transaction)
8. **Zero-trust / security:** ไม่ hardcode secret; validate input ทุกจุด (Zod ฝั่ง client + DRF serializer ฝั่ง server); ไม่ expose password / google_sub_id ใน response

## 9. จุดที่ต้องระวัง (Known Issues / Edge Cases)

1. **Google email ซ้ำกับ manual registration:** ถ้าคนสมัคร email ไว้ก่อน แล้วมา login ด้วย Google email เดียวกัน → โค้ดจะ **link** `google_sub_id` เข้ากับบัญชีเดิม (ไม่สร้างซ้ำ, ไม่แตะ password) แต่ถ้า email นั้นผูกกับ `google_sub_id` อื่นอยู่แล้ว → error `ValueError` (ตอบ 401) กันบัญชีชนกัน
2. **password=NULL (Google-only):** login ด้วย email/password ต้องถูกปฏิเสธ → view เช็ค `if not user.password` คืน `GOOGLE_ONLY_ACCOUNT` 401 (การเปิดเผยว่า "บัญชีนี้เป็น Google" = trade-off ด้าน enumeration — เขียน comment ไว้ในโค้ด)
3. **Refresh token rotation:** เปิด `ROTATE_REFRESH_TOKENS` + `BLACKLIST_AFTER_ROTATION` → token เก่าถูก invalidate ทันทีหลังใช้ 1 ครั้ง → ถ้า frontend เรียก refresh พร้อมกันหลาย tab มีโอกาส tab หนึ่งโดน blacklist (ยังไม่ได้ sync ระหว่าง tab — TODO)
4. **Token เก็บใน localStorage (dev):** refresh token อยู่ใน localStorage → ถ้า XSS จะถูกขโมยได้ — เขียน TODO ใน `token-manager.ts` ว่าก่อน production (R0) ต้องย้ายไป **httpOnly cookie**; access token เก็บใน memory อย่างเดียวอยู่แล้ว
5. **CORS:** ตั้งไว้แล้ว — `http://localhost:3000` และ `http://127.0.0.1:3000` (+ `CORS_ALLOW_CREDENTIALS=True`) อย่าลืมเพิ่ม domain production
6. **register ไม่คืน token:** เป็นดีไซน์ตาม spec §4 (เฉพาะ login/google คืน token) — ถ้าอยากได้ "register แล้ว login อัตโนมัติ" ต้องแก้ฝั่ง backend + frontend ให้ตรงกัน
7. **Error ฝั่ง backend เป็นภาษาอังกฤษ** (เช่น "Invalid email or password") — ยังไม่ทำ i18n ฝั่ง server (frontend แปลเฉพาะ UI + validation ฝั่ง client)
8. **Google id_token ไม่ validate nonce ฝั่ง server** — ป้องกัน replay ได้อีกระดับ (TODO)
9. **Django admin ใช้ได้แล้ว** (`/admin/`) แต่ยังเป็นแบบพื้นฐาน (Custom UserAdmin)
10. **ไม่มี field `picture`/avatar** และ Google login **ไม่ได้** sync ชื่อใหม่ของ user เก่า

## 12. ตัวอย่าง Request/Response

### 12.1 Register
```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/register/ \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"StrongPass123!","first_name":"Somchai","last_name":"Jaidee","phone_number":"0812345678"}'
```
```json
// HTTP 201 — หมายเหตุ: ไม่มี token (ต้องไป /login ต่อ)
{
  "success": true,
  "data": {
    "user": {
      "id": "5f2c...", "username": "test", "email": "test@example.com",
      "first_name": "Somchai", "last_name": "Jaidee", "phone_number": "0812345678",
      "role": "TOURIST", "is_verified": false, "is_active": true,
      "created_at": "...", "updated_at": "..."
    }
  },
  "message": "Registration successful."
}
```

### 12.2 Login
```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/login/ \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"StrongPass123!"}'
```
```json
{
  "success": true,
  "data": {
    "user": { "...": "เหมือน register + role" },
    "access_token": "<jwt>", "refresh_token": "<jwt>"
  },
  "message": "Login successful."
}
```

### 12.3 Google OAuth
```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/oauth/google/ \
  -H "Content-Type: application/json" \
  -d '{"id_token":"<GOOGLE_ID_TOKEN>"}'
```
```json
{
  "success": true,
  "data": {
    "user": { "...": "profile (สร้างใหม่ role=TOURIST หรือ user เดิมที่ถูก link)" },
    "is_new_user": true,
    "access_token": "<jwt>", "refresh_token": "<jwt>"
  },
  "message": "Google sign-in successful."
}
```
