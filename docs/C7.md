## 2. ทำไมเลือกแนวทางนี้ (WHY)

1. **`totalPrice`/`itemCount` ไม่ใช่ state จริง** — recompute จาก `items` ทุกครั้งที่ mutate (`withTotals()`) และ `partialize` เก็บ **เฉพาะ items** ลง localStorage → schema เปลี่ยนทีหลังไม่เหลือข้อมูล stale
2. **Dedupe key = item_type + entity_id + (ห้อง: วันที่เข้าออก)** — add ซ้ำ → เพิ่ม quantity ไม่ duplicate
3. **`entity_id` ไม่ถูกแปลง type ตอนใส่/ตอนออก payload** — wellness ยังเป็น number, UUID ยังเป็น string (C3 §3.2)
4. **`groupedByCategory()` ตาม Q3** — backend ยังไม่มี vendor field → จัดกลุ่มตาม `item_type`; เตรียม path ให้เปลี่ยนเป็น `groupedByVendor` เมื่อ backend เพิ่ม field (TODO Phase 2)
5. **validate input ตอน addItem** — quantity ต้องเป็น int >= 1, price ต้องเป็นจำนวนไม่ติดลบ → store ปฏิเสธของเสียเงียบ ๆ (ZERO TRUST ชั้น client)
6. **`createJSONStorage(() => localStorage)`** — zustand รองรับ SSR อยู่แล้ว (ไม่มี localStorage ฝั่ง server จะข้ามไปอย่างปลอดภัย) — ตรวจสอบอีกรอบตอน typecheck/build

## 3. Known issues / edge cases

- **`removeItem`/`updateQuantity` จับคู่ (entity_id, item_type) เท่านั้น** (ตาม interface ที่ตกลง) — ถ้ามี room line **อันเดียวกันคนละช่วงวันที่ 2 บรรทัด** จะโดนทั้งคู่ (Phase 1 จองห้องเดียวต่อรอบ จึงรับได้ — เขียน note ไว้ในโค้ดหัวไฟล์ #3)
- **ราคาห้อง** `unit_price` เป็นค่าโดยประมาณที่หน้า hotels ส่งเข้า (ราคาจริงแต่ละคืน backend คิดเอง) → ตัวเลขใน cart เป็น estimate; ยอดจริงต้องอ้าง `CheckoutResult.net_amount`
- **`itemCount` = ผลรวม quantity** (ไม่ใช่จำนวนบรรทัด) — ใช้กับ badge ตะกร้า
- Hydration: state ฝั่ง server ว่าง → หลัง rehydrate `merge()` คำนวณ totals ให้จาก items ที่ persist มา
- ยังไม่มี UI ให้ทดลอง — ต้องรอ Module 3–5 หรือ test ด้วยมือตอนมีหน้า
