## 2. ทำไมเลือกแนวทางนี้ (WHY)

1. **Type สะท้อน serializer จริง 1:1** — อ่าน `apps/*/serializers.py` + `views.py` + return ของ `execute_atomic_checkout` ก่อนเขียน:
   - เงิน = **string** (`"1500.00"`) เพราะ DRF DecimalField → กัน float bug
   - `wellness slot.id` = **int** (BIGSERIAL), ตัวอื่น = UUID string → สอดคล้อง C3 §3.2
   - list บางหน้าไม่ใช่ array ตรง ๆ: `rooms` และ `slots` คืน `{ resource, rows[] }` ใน `data` object → มี type `*Result` แยก
2. **`types/api.ts` reuse `ApiErrorEnvelope` เดิม** แทนนิยามซ้ำ — กัน 2 ไฟล์ drift กัน (DISSENT: envelope เคยอยู่ auth แล้ว)
3. **`errors.ts` สร้างใหม่แทน import จาก auth-api** — auth-api ผ่าน review ไปแล้ว (C5 §5 "อย่าแตะ") → แชร์ logic ใหม่ที่นี้ ค่อย merge ใน Phase 2
4. **Wrappers คืน `ApiSuccess<T>` (ทั้ง envelope)** ไม่ใช่แค่ data — เพราะหน้า list ต้องอ่าน `meta.pagination` ต่อ; `auth-api.ts` ทำ pattern เดิมไว้แล้ว
5. **`uploadPaymentSlip` ส่ง multipart** — axios จะทิ้ง content-type JSON ของ instance แล้วให้ browser ใส่ boundary เอง (ไม่งั้น transform เป็น JSON พัง)

## 3. Known issues / edge cases (ที่ FE ต้องรับมือ)

- **Public serializers ไม่มี vendor/owner info** → cart จะจัดกลุ่มตามหมวด (Q3) `vendor_id/vendor_name` เก็บเป็น optional ไว้ก่อน
- **`payee_*` เป็น `""`** (backend ยังไม่ได้ config) → หน้า payment ต้องแสดง placeholder
- **Slip upload = PENDING_CHECK เท่านั้น** (ยังไม่มี provider) → UI ห้ามบอกว่า "ชำระสำเร็จ"
- **`RoomPublic.availability`** เป็น `null` เมื่อ request ไม่ส่ง checkin/checkout; เป็น map `{คืน: จำนวนเหลือ}` เมื่อส่ง
- **Time field** มาเป็น `"HH:MM:SS"` ต้องตัด `:00` ถ้าแสดงแค่ HH:MM
- `BookingDetail.payment` type เป็น nullable กันกรณีไม่มี payment (Phase 1 checkout สร้างเสมอ)
- tab `cancelled` ของ my-orders ฝั่ง backend รวม `PAYMENT_EXPIRED` → UI status badge ต้องรู้จักทั้ง 5 ค่า
- `booking expired` จริง ๆ เกิดที่ Celery worker (backend) — 15 นาที countdown เป็น UI ฝั่ง FE เท่านั้น ไม่ใช่ตัวตัดสิน
