## 1. เป้าหมายและแนวทาง

ทำให้ผู้ใช้สมัคร/เข้าสู่ระบบ เลือกบริการหลายประเภท จองแบบ atomic ชำระด้วยสลิป และเห็นสถานะที่ถูกต้องได้ครบวงจร ขณะเดียวกันผู้ประกอบการจัดการทรัพยากรของตนได้ตามสิทธิ์ โดยไม่ทำให้ราคา สต็อก หรือข้อมูลส่วนตัวเสียหาย

แนะนำ **ซ่อมและเติมทีละเส้นทางบนโครงเดิม**: มี backend permissions, transactions, inventory locking และ frontend modules ให้ต่อยอดแล้ว ไม่พบเหตุผลเพียงพอให้เปลี่ยน stack หรือเขียนใหม่ทั้งหมด

| ทางเลือก | ข้อดี | ข้อเสีย | ข้อเสนอ |
|---|---|---|---|
| A. แก้บนโครงเดิมเป็นชุดเล็ก พร้อม regression | ตรวจ diff ง่าย ใช้ของเดิมได้ และปิดปัญหาที่พบโดยตรง | ต้องไล่สัญญาข้อมูลและ migration อย่างระมัดระวัง | แนะนำ |
| B. เขียน auth/booking/payment ใหม่เป็นชุดใหญ่ | ออกแบบใหม่ได้พร้อมกัน | ขอบเขตกว้าง เสี่ยงสร้างบั๊กใหม่และต้องทดสอบใหม่แทบทั้งหมด | ใช้เฉพาะเมื่อการตรวจเชิงลึกพิสูจน์ว่าโครงเดิมรองรับไม่ได้ |

## 2. สิ่งที่เอกสารล่าสุดช่วยยืนยัน และสิ่งที่ต้องปรับให้ตรงกัน

| หัวข้อ | ภาพรวมล่าสุด / โค้ดและ master เดิม | แนวทางในแผน |
|---|---|---|
| Standard envelope | ภาพรวมกำหนดทุก endpoint; auth client อ่านไม่ตรง | แก้ client ตาม contract ตรวจทุก auth endpoint ไม่เปลี่ยน API ทั้งระบบโดยไม่มีเหตุ |
| Slip Check / payee / worker | อยู่ในเป้าหมาย Phase 1 แต่ master เดิมเลื่อนการเชื่อมจริงไป Phase 2 | จัดเป็นงานทำเส้นทาง Phase 1 ให้ใช้งานได้จริง ไม่อ้างว่ารับเงินพร้อมแล้วเพียงเพราะมีหน้า upload |
| Portal | ภาพรวมต้องจัดการของตนได้; scoped GET/PATCH ยังขาด | เติม API ขั้นต่ำตามงานหน้าจอที่ตกลงไว้; incoming orders แยกออกมาพิจารณาขอบเขต |
| Strict TTL 15 นาที | ภาพรวมระบุชัด แต่ verification อาจมาช้า | คง strict TTL เป็นฐาน ไม่เพิ่ม grace period เงียบ ๆ; เพิ่มเส้นทางจัดการเงินที่ตรวจพบหลัง expiry |
| จำนวน apps | ภาพรวมเขียน 5 แต่แบ่งโค้ดเป็น authentication/accommodations/services/otop/bookings/payments | เอกสารใหม่อ้าง 6 domain apps ตามโค้ด ไม่ย้ายโฟลเดอร์เพื่อให้ตรงตัวเลขในข้อความ |
| จำนวนห้อง | ภาพรวมใช้ total_rooms แต่ model ใช้ total_inventory | ใช้ชื่อจริงใน implementation และทำ mapping ในเอกสาร ไม่สร้าง migration เปลี่ยนชื่อโดยไม่จำเป็น |
| Payment states | ภาพรวมไม่มี FAILED แต่ model มี | ระบุและแสดง FAILED ให้ครบใน contract/UI |
| Hard-delete | ภาพรวมเป็นข้อห้าม แต่ entity_id เป็น string ไม่ใช่ FK ถึงทุกทรัพยากร | ตรวจทุกทาง delete รวม admin/service และป้องกันตามประวัติธุรกรรม ไม่ถือว่า FK ครอบคลุมแล้ว |
| Lock ordering | ภาพรวมระบุ Booking → Payment → Inventory; ต้องตรวจทุก path และลำดับหลาย inventory rows | เขียน lock protocol จริงหนึ่งชุดและใช้ทุก writer พร้อมทดสอบ concurrency |
| ผล 75/75 และ 12/12 | เป็นหลักฐานทดสอบในอดีต ไม่ใช่ผลของการตรวจรอบนี้ | เก็บเป็นประวัติ แล้วสร้าง regression ที่อยู่ใน repository และรันใหม่โดยผู้ใช้ |

## 3. ขอบเขตที่จะทำและสิ่งที่ยังไม่เพิ่ม

**A — ซ่อมของเดิม:** WT-01 ถึง WT-30 ตาม report.md โดยแยกข้อยืนยันจาก code กับข้อที่ต้องพิสูจน์ runtime ก่อนเปลี่ยนโครงสร้าง  
**B — ทำ Phase 1 ให้ครบวงจรตามภาพรวมล่าสุด:** scoped vendor lists/updates ที่จำเป็นกับ portal, payee snapshot, slip provider, Google configuration, worker/recovery และชุดทดสอบที่ทำซ้ำได้

## 4. ลำดับงานและเกณฑ์ตรวจรับ

ลำดับหลัก: **S0 → S1 → S2 → S3 → S4 → S5 → S6 → S7**

### S0 — ตั้ง baseline และล็อก contract
- อ่าน diff/source ปัจจุบันซ้ำก่อนแก้
- สร้างตาราง endpoint/request/response/role/status/error ที่ใช้อยู่จริง
- จัดรายการ WT แต่ละข้อเป็น code-confirmed / ต้อง runtime
- วาง test harness ใน repository และบันทึกคำสั่งที่ผู้ใช้รันได้

### S1 — Auth, session และการแยกข้อมูลผู้ใช้ (WT-01–05, 25, 28)
- แกะ auth envelope ให้ตรง; แก้ auto-link บัญชี manual ที่ยังไม่พิสูจน์เจ้าของ
- ผูก Google callback กับ nonce/state; ล้าง private query/cart เมื่อเปลี่ยน session

### S2 — ราคา สต็อก และเงื่อนไขการจอง (WT-06–10, 17–19)
- ตรวจราคา > 0; ล็อก wellness service ขณะตรวจ overlap (ตอบ 409)
- ใช้ timezone Asia/Bangkok; จำกัดจำนวนคืน/horizon/cart lines; จัด lock order ให้ deterministic

### S3 — Cart และ checkout ที่ส่งซ้ำได้อย่างปลอดภัย (WT-16, 20, 25)
- Cart line identity ครอบคลุมช่วงวัน/slot; เพิ่ม Idempotency key ต่อ checkout attempt
- retry ด้วย key เดิมเมื่อ network timeout; clear cart หลัง server ยืนยันสำเร็จ

### S4 — Payment, private slip และ expiry ที่กู้คืนได้ (WT-11–15, 21–22, 26, 28)
- Payee account จาก config; เพิ่ม `expires_at` ใน Payment API response
- Private storage สำหรับรูปสลิป; เชื่อม Slip provider adapter; strict TTL 15 นาที + recovery handler

### S5 — Portal ให้ทำงานตามบทบาทได้ครบ (WT-23–25)
- Scoped GET (เห็นของตนเองรวมปิดขาย) + PATCH field-level
- Homestay, Restaurant, Wellness, OTOP แยกการทำงานตาม role + ล็อค ownership

### S6 — หน้าบ้านและ production hardening (WT-19, 24, 26–30)
- Pagination ประวัติการจอง; i18n TH/EN ครบ; Mobile 390/430px & Desktop responsive
- Production storage / static serving / Sanitized errors / Security rate limits

### S7 — ตรวจรับและเตรียมเปิดจริง
- รัน backend tests บน PostgreSQL จริง; รัน frontend typecheck & build; E2E integration test
